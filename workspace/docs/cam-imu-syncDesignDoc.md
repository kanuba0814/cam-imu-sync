相机-IMU 软件同步设计文档
1. 文档目的

本文档用于定义一套面向 30 FPS 相机与 200 Hz IMU 的软件同步方案。目标是在不改动 IMU 固件、不依赖严格硬件锁相的前提下，实现稳定、低延迟、可工程化落地的同步数据流输出，用于 VIO、SLAM、时序分析与传感器融合等场景。

本方案基于 H30 / Yesense YIS 系列设备的现有能力设计：模块支持 UART、I2C、同步输入和同步输出，最高输出频率为 200 Hz；其中 YIS106 的外部同步输入最高仅支持 20 Hz，I2C 通信需要配合 INT/DR 数据就绪信号使用。

2. 设计目标
2.1 目标
建立统一的相机-IMU 时间轴
以图像帧为主时钟，对 IMU 数据段进行裁剪与边界插值
输出可直接供下游算法消费的同步图像流与同步 IMU 流
在串口抖动、线程调度抖动、少量丢包情况下仍能稳定工作
为后续外参标定、时延标定、VIO 接入预留扩展空间
2.2 非目标
不追求“逐帧硬触发式绝对物理同步”
不修改 IMU 底层固件
不依赖相机帧触发 IMU 每次采样
不使用设备内部融合后的欧拉角/四元数作为主同步数据
3. 已知硬件与协议约束
3.1 IMU 频率与接口能力

H30 / YIS106 支持 UART 和 I2C 通信，最高输出频率为 200 Hz。

3.2 同步输入限制

YIS106 的同步输入引脚支持外部触发采样，但可接收的同步信号最高频率仅为 20 Hz，通常建议使用 1 Hz。因此无法直接以 30 FPS 图像帧作为每帧硬件同步触发源。

3.3 I2C 读取限制

YIS106 的 I2C 通信必须配合 INT/DR 引脚，只有在数据就绪信号上升沿出现后，主机才能读取有效数据；文档还说明 I2C 通信仅能在 DR 上升沿后 5 ms 内读取。H30 手册也明确说明 IIC 无数据时，应等待 INT 拉高并通过外部中断捕获。

3.4 协议时间戳能力

协议支持：

0x51 采样时间戳
0x52 同步输出时间戳

这些字段可作为 IMU 时间轴重建的优先参考。

4. 核心设计结论

200 Hz IMU 与 30 FPS 相机之间不是点对点同步，而是“区间同步 + 边界插值”。

原因如下：

IMU 周期：5 ms
相机周期：33.333 ms

一帧图像天然覆盖约 6~7 个 IMU 采样周期，因此正确策略不是“给每帧图像找一个 IMU 点”，而是“给每帧图像匹配一个 IMU 时间区间，并在图像时刻做边界插值”。

5. 总体架构

系统采用“四部分”结构：

主控线程
IMU 采集线程
相机采集线程
同步处理线程
5.1 主控线程

负责：

参数加载
子线程启动与关闭
运行状态监控
异常恢复
统计信息输出

主控线程不参与热路径数据处理。

5.2 IMU 采集线程

负责：

从 UART / I2C 接收原始数据
协议解包
解析 accel / gyro / timestamp
构造统一 IMU 样本
写入 IMU 环形缓冲区

IMU 线程只做采集与入队，不做同步计算。

5.3 相机采集线程

负责：

接收图像消息
提取图像时间戳
构造帧样本
写入图像队列

相机线程只负责收图，不做对齐逻辑。

5.4 同步处理线程

负责：

以图像时间为主时钟
从 IMU 缓冲区中提取 (t_prev, t_img] 区间样本
必要时在 t_img 处做线性插值
先发布同步后的 IMU，再发布同步后的图像
6. 时间基准设计
6.1 主时钟选择

本方案以图像时间戳为主时钟。
每当收到一帧图像，系统在 IMU 时间轴上找到与该帧对应的时间区间。

定义：

图像原始时间：t_cam
相机到 IMU 的固定时间偏移：offset
对齐目标时间：t_align = t_cam + offset

同步器以 t_align 作为本帧图像对应的统一对齐时刻。

6.2 IMU 时间戳优先级

IMU 时间戳来源优先级定义如下：

协议中的 sample_timestamp (0x51)
协议中的 sync_out_timestamp (0x52) 或帧号辅助推算
接收线程的系统时间 now() 兜底

不建议直接以“串口读到数据的时刻”作为主 IMU 时间戳，因为该时间受调度抖动影响较大。

6.3 相机时间戳优先级

图像时间戳优先级定义如下：

驱动硬件时间戳
V4L2 / 驱动层采集时间
ROS 消息 header.stamp
回调接收时刻 now() 兜底
7. 数据结构设计
7.1 IMU 样本结构
struct ImuSample {
    double t;              // 统一时间轴下的时间，单位秒
    Vec3 gyro;             // 角速度
    Vec3 accel;            // 线加速度
    uint32_t seq;          // 序号
    bool interpolated;     // 是否由插值得到
};
7.2 图像样本结构
struct FrameSample {
    double t_cam;          // 图像原始时间
    double t_align;        // 校正后时间
    ImageMsg img;          // 图像数据
    uint64_t frame_id;     // 帧号
};
8. 缓冲区设计
8.1 IMU 缓冲区

建议使用按时间有序的 deque 或环形缓冲区。

参数建议
缓冲长度：2~3 秒
200 Hz 条件下：约 400~600 个样本
超时样本自动清理
设计要求
支持按时间范围快速查找
支持头部批量丢弃旧数据
支持读写线程并发访问
支持插值前后邻点检索
8.2 图像队列

建议长度较小，避免同步处理滞后引发积压。

参数建议
队列长度：10~30 帧
设计要求
若队列持续增长，说明同步线程跟不上，应告警
必须保证时间单调递增
9. 同步算法设计
9.1 基本流程

对于每一帧图像：

取出图像 img
计算 t_align = img.t_cam + offset
在 IMU 缓冲区中等待，直到最新 IMU 时间 >= t_align
提取 (t_prev_align, t_align] 区间中的 IMU 样本
若最后一个样本时间不等于 t_align，则在边界做插值
发布该区间 IMU 数据
发布该帧图像
更新 t_prev_align = t_align
9.2 区间同步原则

每帧图像对应一段 IMU 序列，而不是一个 IMU 点。
在 30 FPS 与 200 Hz 条件下，通常每帧对应：

6~7 个原始 IMU 样本
0~1 个边界插值样本
9.3 插值策略

对以下数据做线性插值：

angular_velocity
linear_acceleration

公式：

alpha = (t_align - t0) / (t1 - t0)
x_align = (1 - alpha) * x0 + alpha * x1
不建议插值的数据
欧拉角
四元数
设备内部融合姿态

原因是下游 VIO 更依赖原始惯性量，融合后的姿态角会引入内部滤波与磁参考误差。

10. 线程协作逻辑
10.1 IMU 采集线程伪流程
循环:
  读取串口/I2C
  解包协议
  解析 accel/gyro/timestamp
  构造 ImuSample
  push 到 imu_buffer
  清理过旧样本
10.2 相机采集线程伪流程
收到图像:
  提取时间戳
  计算或记录 frame_id
  构造 FrameSample
  push 到 image_queue
10.3 同步处理线程伪流程
循环:
  若 image_queue 为空，等待
  取队首图像
  计算 t_align

  若 imu_buffer 最新时间 < t_align:
      继续等待

  否则:
      提取 (t_prev_align, t_align] 区间 IMU
      检查是否需要边界插值
      生成同步 IMU 批
      发布同步 IMU
      发布同步图像
      更新 t_prev_align
      弹出当前图像
11. 发布接口设计

建议输出以下 Topic：

/sync/imu
/sync/image_raw
11.1 发布时间顺序

必须先发布 IMU，再发布图像。

原因是下游算法通常在图像回调触发时立即消费“本帧之前的 IMU 区间”。若先发图像，后发 IMU，可能出现图像已到但 IMU 尚未齐备的情况。

11.2 时间戳规则
/sync/image_raw 使用 t_align
/sync/imu 中所有样本使用统一时间轴
边界插值样本时间应精确等于 t_align
12. 参数设计

建议支持以下运行参数：

cam_imu_time_offset: 0.0
imu_buffer_sec: 3.0
max_sync_wait_ms: 100
enable_interpolation: true
max_interp_gap_ms: 10
drop_frame_on_missing_imu: true
warn_on_queue_backlog: true
参数说明
cam_imu_time_offset：相机相对 IMU 的固定时间偏移
imu_buffer_sec：IMU 缓冲区保留时长
max_sync_wait_ms：图像等待 IMU 覆盖的最长时间
enable_interpolation：是否启用边界插值
max_interp_gap_ms：允许插值的最大 IMU 间隔
drop_frame_on_missing_imu：IMU 缺失时是否丢弃图像
warn_on_queue_backlog：积压时是否告警
13. 异常处理设计
13.1 图像到达但 IMU 尚未覆盖 t_align

处理策略：

暂不发布
继续等待后续 IMU 到达
超时后触发丢帧逻辑
13.2 IMU 长时间中断

处理策略：

丢弃等待中的图像
清空同步状态
记录错误计数
打印告警日志
13.3 IMU 丢包或时间间隔过大

处理策略：

若相邻 IMU 时间差超过 max_interp_gap_ms
禁止插值
当前帧标记失败或直接丢弃
13.4 时间戳跳变 / 回退

处理策略：

清空 IMU 缓冲区
清空图像队列
重置 t_prev_align
重新建立同步状态
13.5 队列积压

处理策略：

当图像队列长度持续上升时，说明同步线程处理能力不足
触发告警
必要时启用丢帧保护
14. 统计与监控指标

建议实时统计：

已同步图像帧数
已丢弃图像帧数
平均每帧匹配到的 IMU 数量
插值使用次数
IMU 实际输入频率
图像实际输入频率
IMU 缓冲区当前深度
图像队列当前深度
同步等待超时次数
时间戳异常次数
15. 验收标准

满足以下条件，可认为方案达到工程可用状态：

在 30 FPS + 200 Hz 条件下连续运行 10 分钟 无线程阻塞、无明显积压
/sync/image_raw 时间戳单调递增
/sync/imu 时间戳单调递增
每帧图像都能获得对应的 IMU 区间
边界插值点时间误差小于 0.1 ms
下游算法不再出现“图像已到但 IMU 不足”的报错
轻微串口抖动下同步质量不显著下降
16. 实现建议
16.1 推荐输入数据内容

建议只同步以下 IMU 原始量：

加速度
角速度
硬件时间戳

不建议以欧拉角、四元数作为主同步内容。

16.2 接口推荐

若当前使用 ROS2，可在节点内部拆成：

imu_receiver
camera_receiver
sync_manager

也可封装为单节点多线程模型。

16.3 锁与性能建议
IMU 缓冲区使用细粒度互斥锁
图像队列与 IMU 缓冲区分离锁
同步线程避免长时间持锁
插值与区间拷贝应在锁外完成
17. 结论

本方案在现有 H30 / Yesense YIS 设备能力下，是一套可直接落地的软件同步实现路径。

结论如下：

由于 IMU 最高输出 200 Hz、外部同步输入最高仅 20 Hz，无法实现与 30 FPS 图像逐帧硬件锁相。
由于设备协议支持采样时间戳与同步输出时间戳，软件侧可以基于硬件时间轴实现高质量软同步。
最合适的工程方案是：图像主时钟 + IMU 区间同步 + 边界插值 + 统一时间轴发布。

最终推荐将该系统定义为：

一个协调节点统一拉起 IMU 接收线程、相机接收线程和同步处理线程；同步器以图像时间为主时钟，在 IMU 时间轴上提取区间数据，并在图像边界处进行线性插值，随后发布同步后的图像与 IMU 数据流。
